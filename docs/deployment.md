# Deployment

MCP OAuth Server is a self-hosted ASP.NET Core service. It issues tokens for MCP servers and must be reachable over public HTTPS.

## Requirements

- .NET 10.0 runtime, or a published self-contained build
- A public HTTPS hostname matching `oAuthServerSettings.issuer`
- Durable, writable storage for the four JSON stores and the signing key
- A secret provider for the signing key path and account hashes

## Process Topology

Run one instance per issuer URL. All state lives in the configured JSON files, and the server keeps no in-memory session state beyond cached signing credentials. Because writes are not coordinated between processes, run a single instance unless the stores are replaced with a shared implementation.

## TLS Termination

Terminate TLS at a reverse proxy and forward requests to Kestrel over the loopback interface. The issuer URL must reflect the public HTTPS origin, not the internal listener, because clients compare the published metadata `issuer` with the `iss` parameter byte-for-byte.

Do not expose the application over plain HTTP in production. Loopback HTTP redirect URIs are accepted only for desktop client development.

## Signing Key

The RSA signing key is a PKCS#8 PEM file. When absent, a new 2048-bit key is generated and the file is restricted to owner read and write on non-Windows platforms.

- Persist the key across restarts. Replacing it invalidates every previously issued token.
- Provide the key out of band, or generate it once on first start and move it into the secret store.
- Never commit a production key. The default `Data/` directory is excluded from version control.
- Publish rotation by adding a second key to the JSON Web Key Set before switching signing credentials; this release publishes a single key.

## Persistence

| Store | Contents | Backup Requirement |
|-------|----------|--------------------|
| `clients.json` | Registered and predefined clients, including secret hashes | Yes, so registrations survive replacement |
| `users.json` | Seeded accounts and password hashes | Yes |
| `authorisation-codes.json` | Unconsumed authorisation codes | No, these are short-lived |
| `refresh-tokens.json` | Active refresh tokens | Yes when refresh continuity matters |
| `signing-key.pem` | RSA private key | Yes, and treat it as a secret |

Suspend the service, then copy the files to create a consistent backup. Restore by placing valid copies at the configured paths before starting the service.

## Configuration and Secrets

Set `OAuthServerSettings__Issuer`, `OAuthServerSettings__SigningKeyPath`, and `OAuthServerSettings__AllowedResources__0` through the platform's environment or secret configuration. Provide password hashes generated by `generate-password-hash`; never store plaintext passwords in configuration or source control.

## Health and Observability

Microsoft.AspNetCore.Hosting exposes framework lifecycle logs. The application emits structured operation events through NuciLog, optionally to a file. Client identifiers, user identifiers, scopes, and audiences appear in logs; passwords, secrets, tokens, and authorisation codes do not.

No dedicated health endpoint exists. Use an unauthenticated `GET /.well-known/oauth-authorization-server` as a readiness probe.

## Scaling

- Configure the longest practical authorisation-code lifetime for the number of instances; codes are single-use across the store.
- Refresh tokens are rotated on every exchange, so concurrent refreshes from one connection invalidate each other by design.
- Serve the discovery, JWKS, token, and userinfo endpoints behind a cache only when the cache respects `no-store` for token and userinfo responses.

## Upgrading

1. Back up `clients.json`, `users.json`, `refresh-tokens.json`, and the signing key.
2. Deploy the new build into a fresh directory.
3. Start the service and confirm discovery responds.
4. Verify one complete authorisation-code flow before reconnecting ChatGPT.
